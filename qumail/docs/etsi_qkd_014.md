# ETSI GS QKD 014 — as implemented in QuMail

This note documents the subset of **ETSI GS QKD 014** ("Protocol and data
format of REST-based key delivery API") that QuMail's KM Client (M4) and KM
Simulator (M6) implement, and the conventions both sides agree on. Field names
are taken verbatim from the standard and must not be renamed.

## 1. Roles

- **SAE** (Secure Application Entity): an endpoint that consumes keys — here, a
  QuMail user. Identified by a `SAE_ID`.
- **KME** (Key Management Entity): the Key Manager serving keys to SAEs. The
  simulator plays this role in development; real QKD hardware plays it in
  production.
- **Master SAE** requests encryption keys (`enc_keys`) and shares the returned
  `key_ID`(s) with the peer over the email metadata. **Slave SAE** redeems those
  IDs via `dec_keys`.

## 2. Endpoints

Base path: `/api/v1/keys`. All bodies are JSON.

### `GET /api/v1/keys/{SAE_ID}/status`
Returns a status document for the calling SAE.
```json
{
  "source_KME_ID": "KME-SIM-001", "target_KME_ID": "KME-SIM-002",
  "master_SAE_ID": "SAE-ALICE",   "slave_SAE_ID": "SAE-BOB",
  "key_size": 256, "stored_key_count": 42, "max_key_count": 1024,
  "max_key_per_request": 8, "max_key_size": 65536, "min_key_size": 64
}
```

### `POST /api/v1/keys/{slave_SAE_ID}/enc_keys`
Master SAE requests fresh keys for encrypting toward the named peer.
Request: `{ "number": 1, "size": 256 }` (size in **bits**, a multiple of 8).
Response — a **key container**:
```json
{ "keys": [ { "key_ID": "QK-000123", "key": "<base64 key bytes>" } ] }
```

### `POST /api/v1/keys/{master_SAE_ID}/dec_keys`
Slave SAE redeems key IDs received from the master.
Request: `{ "key_IDs": [ { "key_ID": "QK-000123" } ] }`
Response: the same key-container shape, returning the matching key bytes.

## 3. Fixed field names

`key_ID`, `key` (base64), `keys`, `number`, `size`, `key_IDs`,
`stored_key_count`, `*_SAE_ID`, `*_KME_ID`. QuMail models these in
`core/models.py` (`ETSIKey`, `ETSIKeyContainer`, `ETSIKeyRequest`,
`ETSIKeyIDsRequest`, `ETSIStatus`) and reuses them on both the client and the
simulator so the wire shapes cannot drift.

## 4. Handoff flow

```
Alice (master)                     KME / QKD                  Bob (slave)
  │  POST enc_keys {number,size}      │                          │
  │ ─────────────────────────────────▶                          │
  │  ◀───────────────  {keys:[{key_ID, key}]}                    │
  │  encrypt with key; email carries key_ID in .qenc metadata ──▶│
  │                                   │   POST dec_keys {key_IDs} │
  │                                   ◀───────────────────────────
  │                                   │ ──▶ {keys:[{key_ID,key}]} │
  │                                   │        decrypt with key    │
```

## 5. Simulator specifics (M6, dev only)

- Keys are generated by a Qiskit QRNG (Hadamard-per-qubit measurement), with an
  OS-CSPRNG fallback when Qiskit is not installed.
- `key_ID` format: `QK-NNNNNN` (zero-padded counter). Keys are held in an
  in-memory store keyed by `key_ID`.
- A `bb84.py` module simulates the BB84 protocol (sifting + QBER) for teaching
  and demos; it is not on the key-delivery path.
- **No authentication** in the simulator (a `TODO` hook marks where mutual TLS +
  SAE certificates belong for real deployments).

## 6. Swapping in real hardware

The client speaks only this REST surface, so pointing QuMail at real QKD
hardware is a **`base_url` change**: set `KM_BASE_URL` in `.env`, or call
`POST /auth/km` with the hardware KME's URL and the real `sae_id`. No client
code changes. TLS verification is on by default (`verify_tls=true`); disable it
only for the local plain-HTTP simulator.
